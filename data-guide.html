From static to live

Wiring up live scores

The site reads from one seed file, assets/data.js. To make scores update on their own, you fetch from an API and pour the result into the same WC object the pages already read. This build uses API-Football, which works straight from the browser, so no server is needed on GitHub Pages.

Why API-Football and not football-data.org? football-data.org blocks direct browser calls (CORS), so it needs a server in the middle. API-Football allows browser calls with the key in a request header, which is what makes a no-server GitHub Pages setup possible. The tradeoff is the key is visible in your code. For a free portfolio demo that is acceptable since it only reads public scores and is rate-limited to 100 calls a day. Step 5 covers hiding it if you want.

1 · Get your free API key

Sign up

Go to dashboard.api-football.com/register and create a free account. No card needed.

Confirm your email

Click the link they send. The free plan gives you 100 requests per day with access to every endpoint.

Copy your key

On the dashboard, your key sits under API Key or My Access. It is a long string. You send it in a header called x-apisports-key on every request.

Note: sign up through dashboard.api-football.com (the direct API-SPORTS account), not through RapidAPI. The direct account uses the simple x-apisports-key header this guide expects.

2 · Test the key (the right way)

Do not open the page by double-clicking the file. That runs it from file:// with no real origin, and the API rejects it. Instead, run a tiny local server first, then test in the console.

Start a local server

In a terminal, inside your project folder, run one of these. Then visit the address it prints (usually http://localhost:8000).

# if you have Python
python -m http.server 8000

# or if you have Node
npx serve

Then test in the browser console

With the page open on localhost, press F12, open Console, paste this, and swap in your key. Type the quotes by hand so they stay straight, not curly.

const KEY = "PASTE_YOUR_KEY_HERE";
fetch("https://v3.football.api-sports.io/fixtures?league=1&season=2026", {
  headers: { "x-apisports-key": KEY }
})
  .then(r => r.json())
  .then(d => {
    console.log(d.results, "fixtures loaded");
    console.log(d.response[0]);
  })
  .catch(e => console.error("Failed:", e));

If it prints a fixture count, you are connected. If you see errors in the response with a token message, the key is wrong or missing. A 429 means you used up the daily 100.

3 · The file that does the work

The site already ships with assets/live.js. It does three things: holds your key, fetches fixtures and standings, and translates API-Football's shape into the WC object the pages read. You do not need to write it. You only need to:

  • Open assets/live.js and paste your key into the API.key line at the top.
  • Make sure each page loads it (next step).

It already handles the two gotchas: API-Football returns team names not flag codes, so there is a lookup table inside that maps all 48 teams to the right flag. And it derives each match's group letter from the standings, since the fixtures feed does not include it directly.

4 · Switch each page from seed to live

Right now every page ends with a block that renders immediately from seed data. To go live, add live.js after app.js, then wrap the render code so it runs after the fetch finishes. The pattern is the same on every page:

<script src="assets/data.js"></script>
<script src="assets/app.js"></script>
<script src="assets/live.js"></script>
<script>
  mountNav("index.html");
  mountFoot();

  async function start() {
    await goLive();        // fills WC from the API (or keeps seed on failure)
    renderPage();          // the page's existing render code, moved into here
  }
  start();
</script>

So on the home page, for example, you take everything that currently runs after mountFoot(), wrap it in a function renderPage(), and call start(). Because goLive() falls back to seed data if the network fails, the site never shows up empty.

Watch your request budget. The free tier is 100 calls a day. Each page load calls the API twice (fixtures plus standings). Browsing your own site a few dozen times in testing can eat that fast, so do most of your design work on the seed data and only flip to live when you want to see it move.

5 · Hiding the key (optional)

For a portfolio demo, a visible read-only key that is rate-limited is a normal tradeoff. If you want it hidden later, the standard fix is a free serverless proxy that holds the key and forwards the request:

  • Cloudflare Workers or Vercel functions, free tier. Store the key as an environment variable, fetch the API from there, and have your site call the worker instead.
  • Your live.js then points at your-worker.workers.dev with no key in the page.

Start with the key in live.js, get the site moving, then add a proxy if you decide to.

6 · Auto-refresh during live games

To make scores tick without a reload, re-run the fetch on a timer. Every 60 seconds keeps you well inside the daily limit during a match window:

setInterval(async () => {
  await goLive();
  renderPage();
}, 60000);   // 60 seconds
The whole swap in one breath: sign up, paste your key into live.js, add the live.js script tag to each page, wrap each page's render code in renderPage() and call it after goLive(). Players and formations stay hand-curated in data.js, since the free tier does not carry Football Manager style attribute ratings. That editorial layer is what makes the site yours.
